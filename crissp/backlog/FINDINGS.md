| F-01 | src/crissp/cli.py (2026-11-05) | crissp refused every option meant for a guard (crissp check --plan, crissp deploy --cluster, crissp ux --shoot <walk>): argparse's REMAINDER does not pass a leading --option on to a subcommand. Found while building the README's demo; the package test only ran commands without options. Fixed: crissp splits the command line at the guard's name and passes the rest untouched; test_cli.py proves every guard's options (red before, green after). | fixed (0.1.0, before the first commit) |
| F-02 | crissp/uxsuite/ux_backlog.py (2026-11-05) | Approving a design in an installed project (crissp init) failed with 400 "crissp/tool/server.py is missing": the UX suite only looked for the crissp tool inside the project, which a package-installed project no longer has. Its tests missed it because their example project carries a copy of the tool. Found by clicking Approve in the README demo. Fixed: the project's own tool, else the engine's (test_an_installed_project_writes_with_the_engines_tool, red before, green after). Also added: Before / After in every design (the walk's screenshot on laptop or phone next to the mockup, same size) with Approve right under it. | fixed (0.1.0, before the first commit) |
| F-03 | crissp/check-all.sh, the first full run (2026-11-05) | The CVE audit flagged pytest 8.4.2 (PYSEC-2026-1845: on UNIX it relies on /tmp/pytest-of-user directories, local users can cause a denial of service or worse); and test_ux_sh_lists_reports_and_refuses_what_it_does_not_know read the run's own project (inherited CRISSP_ROOT) instead of its copy, so it failed only inside a full run. Fixed in 07df295: pytest 9.0.3 pinned, the test starts ux.sh without CRISSP_ROOT; the next full run was green. | fixed (0.1.0, 07df295) |
| F-04 | crissp 0.1.0.dev1 from TestPyPI, a new project (2026-11-05) | In a project made with crissp init the guards still speak of their script paths: "Green: crissp/deploy.sh may go", "run crissp/check-all.sh again", "crissp/ux.sh --shoot". Those files do not exist in such a project (the engine is in the package); it should say crissp deploy, crissp check-all, crissp ux --shoot. | the product owner (next release) |
| F-05 | crissp 0.1.0.dev1 from TestPyPI, .mcp.json (2026-11-05) | crissp init pins .mcp.json to uvx crissp==0.1.0.dev1 mcp, but a dev build lives on TestPyPI only, so Claude Code's plain uvx cannot find it and the crissp tool does not start in a project made from a test build. Fine for a real release (on PyPI). Either write the index into .mcp.json for a dev version, or say so in the README's TestPyPI note. | the product owner (before testing with Claude Code on a dev build) |
| F-06 | crissp 0.1.0.dev1 from TestPyPI, the first full run (2026-11-05) | A new project's first crissp check-all is green but ends with "The coverage baseline went up: commit crissp/testsuite/coverage-baseline.json": a new user must commit once more before crissp check moves the certificate. On a first run the baseline could be written as part of init (empty), or the message could say plainly that this is the first baseline. | the product owner (next release) |
| F-07 | GitHub Actions, the publish workflow's build job (2026-11-05) | "Unable to resolve action astral-sh/setup-uv@v10": Astral publishes full version tags only (v10.3.3), no moving major tag, so the Node 24 update broke ci.yml and publish.yml. The update checked each action's runtime but not that its tag resolves; the other seven tags (checkout v7, configure-pages v6, upload-pages-artifact v5, deploy-pages v5, upload-artifact v7, download-artifact v8, setup-helm v5) were checked against their tag lists and exist. Fixed: setup-uv@v10.3.3. | fixed (0.1.0) |
| F-08 | crissp/check-all.sh, three runs in a row (2026-11-05) | Every green full run rewrote coverage-baseline.json with only a new commit hash (the numbers unchanged), so every full run asked for an extra commit ("the coverage baseline went up") although nothing went up; this hits every project, after every full run. Fixed in lib/gate.py: the baseline is written only when something moves (no baseline yet, --accept, a number that changed, or a commit the diff rule needs because none is recorded or git no longer knows it); otherwise the older commit stays and the next diff rule looks back further, stricter, never laxer. | fixed (0.1.0) |
